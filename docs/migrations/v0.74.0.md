# Migrating to v0.74.0

## delete is the one removal verb

**Before:** four command groups removed things with `remove` while `secrets`
and `subscriptions` used `delete`.

**After:** every group uses `delete`, with the same flags as before:

| Before | After |
|---|---|
| `sparkwing pipeline sparks remove --spark NAME` | `sparkwing pipeline sparks delete --spark NAME` |
| `sparkwing profiles remove --profile NAME` | `sparkwing profiles delete --profile NAME` |
| `sparkwing repos remove` | `sparkwing repos delete` |
| `sparkwing runners remove --profile NAME` | `sparkwing runners delete --profile NAME` |

An old spelling is refused with a usage error that names the `delete` command,
and nothing runs. Update scripts that call the old spellings.

## Run and plan flags lose their prefix

**Before:** `sparkwing run` and `sparkwing pipeline plan` spelled their own
flags with a `--sw-` prefix, while `pipeline trigger` used plain names such as
`--detach` and `--ref`.

**After:** the three commands share one set of plain names. Pipeline arguments
still follow `--`, so a pipeline keeps every flag name for itself. The old
spellings are refused with a usage error that names the new flag, and nothing
runs.

| Before | After |
|---|---|
| `--sw-detached` | `--detach` |
| `--sw-dry-run` | `--dry-run` (also on `pipeline plan`) |
| `--sw-ref` | `--ref` |
| `--sw-pipeline-ref` | `--pipeline-ref` |
| `--sw-route` | `--route` |
| `--sw-allow-risk` | `--allow-risk` |
| `--sw-allow-unadmitted` | `--allow-unadmitted` |
| `--sw-only` | `--only` |
| `--sw-start-at` | `--start-at` |
| `--sw-stop-at` | `--stop-at` |
| `--sw-no-memo` | `--no-memo` |
| `--sw-workers` | `--workers` |
| `--sw-priority` | `--priority` |
| `--sw-no-update` | `--no-update` |
| `--sw-no-bincache` | `--no-bincache` |
| `--sw-hash-all-files` | `--hash-all-files` |
| `--sw-cache-from` | `--cache-from` |
| `--sw-pause-before` | `--pause-before` |
| `--sw-pause-after` | `--pause-after` |
| `--sw-pause-on-failure` | `--pause-on-failure` |
| `--sw-idempotency-key` | `--idempotency-key` |
| `--sw-request-id` | `--request-id` |
| `--sw-run-handle-file` | `--run-handle-file` |
| `--sw-index` | `--index` |
| `--sw-verbose` (`-v`) | `--verbose` (`-v`) |

Update every script, CI workflow, git hook and cron entry that starts a run.
For example, a standalone CI step becomes:

```sh
sparkwing run release --allow-unadmitted --workers=4 --no-update
```

and a detached, risk-authorized run becomes:

```sh
sparkwing run deploy --detach --allow-risk destructive,prod -- --region us-east
```

**Upgrade the pipeline first.** `sparkwing run` hands its flags to the engine
that the pipeline's SDK pin selects. An engine older than v0.74.0 does not know
the new names, and this CLI no longer accepts the old ones. Until the pin moves,
a run that passes any of these flags is refused before it starts, with an error
that says so. Run this in each repository after updating the CLI:

```sh
sparkwing pipeline upgrade
```

A run that passes none of these flags keeps working on the older engine. The
internal SDK protocol arguments keep their names.

## runs grep is the one log search

**Before:** `sparkwing runs logs --grep PATTERN` without `--run` searched across
runs with the same filters as `runs grep`, and `runs logs --run ID --grep
PATTERN` filtered one run's lines.

**After:** `runs logs` reads one run and requires `--run`. `runs grep` does all
searching:

| Before | After |
|---|---|
| `sparkwing runs logs --grep fatal --pipeline check` | `sparkwing runs grep --grep fatal --pipeline check` |
| `sparkwing runs logs --run RUN_ID --grep fatal` | `sparkwing runs grep --run RUN_ID --grep fatal` |

`sparkwing runs grep --run RUN_ID --grep P` replaces a `--grep` on
`runs logs --run RUN_ID`. It applies the same Go regular expression on the controller to the
run's output lines, lifecycle events and their fields, and prints the matching
records in the `runs logs` output formats. With `--run`, `runs grep` takes only
`--job`, `--grep`, `--since` and `--profile`; the cross-run filters, `--limit`,
`--max-matches`, `--quiet` and `--cursor` are refused with `--run`. A `--grep`
on `runs logs` is refused with a usage error that names `runs grep`.

The per-run reading options of `runs logs` no longer combine with a pattern.
For `--follow`, `--head`, `--tail` and `--lines`, read the run with `runs logs`
and filter its plain output:

| Before | After |
|---|---|
| `sparkwing runs logs --run RUN_ID --grep P --follow` | `sparkwing runs logs --run RUN_ID --follow -o plain \| grep -E P` |
| `sparkwing runs logs --run RUN_ID --grep P --head 50` | `sparkwing runs logs --run RUN_ID --head 50 -o plain \| grep -E P` |
| `sparkwing runs logs --run RUN_ID --grep P --tail 50` | `sparkwing runs logs --run RUN_ID --tail 50 -o plain \| grep -E P` |
| `sparkwing runs logs --run RUN_ID --grep P --lines A:B` | `sparkwing runs logs --run RUN_ID --lines A:B -o plain \| grep -E P` |

The pipe is not the same search. It matches the rendered plain text with
`grep -E` rules, not the controller's Go regular expression, so it can miss
matches the old form found: lifecycle events and structured fields that plain
output leaves out or renders differently, and patterns that only Go's syntax
accepts, such as `\d` or `(?i)`. `--head`, `--tail` and `--lines` still count a
log's lines before the filter. With `--follow`, add `--line-buffered` to `grep`
when piping further.

`--tree`, `--events-only` and `--no-events` have no pattern form. `runs grep
--run RUN_ID` searches the run's output and events together and does not
descend into child runs; search each child run by its own ID.

## The saved default profile and machine run route are removed

**Before:** `sparkwing profiles set --profile NAME --default` saved
`default: true` on a profile in the machine config, and every command with an
optional `--profile` sent its request to that controller when the flag was
omitted.

**After:** a command reaches a controller only when its invocation asks for one:
`--profile NAME`, or for `sparkwing run` an explicit `--route cloud` or
`--route burst`, which uses `run.routing.profile` when `--profile` is absent.
Without either, or with `--profile=`, the command uses the local controller.
`profiles set` no longer takes `--default`, `profiles list` and `profiles show` no longer
report `default`, and a config file that still carries `default: true` fails to
load with:

```text
profiles.NAME.default: line N: was removed; pass --profile NAME on each command that should reach that controller (see `sparkwing docs migrations`)
```

To migrate:

1. Delete the `default:` line from each profile in the machine config, the
   file the load error names.
2. Add `--profile NAME` to scripts, aliases and shell habits that relied on the
   default, for example `sparkwing runs list --profile prod`.
3. Reinstall schedules that should reach a controller with an explicit
   `--profile`; ones installed without it act on this machine. Managed git hooks
   run `sparkwing run` without `--route`, so they now always run locally.

`SPARKWING_PROFILE` never selected a connection and still does not.

### Machine `run.routing.route`

**Before:** `route: cloud` under `run.routing` in the machine config sent every
bare `sparkwing run` through Cloud overflow, including runs from git hooks and
scripts that never named a route.

**After:** a run leaves this machine only when the invocation asks.
`--route burst` applies the machine `run.routing` preferences, overflow
allowance and local fallback; `--route cloud` still runs directly on Cloud.
A run without `--route` is local. A config that still carries
`run.routing.route` fails to load and names this change.

To migrate, delete `route:` from `run.routing` and add `--route burst` to the
runs that should overflow, for example `sparkwing run test --route burst`.
The other `run.routing` keys (`profile`, `prefer`, `overflow_minutes`,
`local_secrets`, `source_files`) keep their meaning.

## Queue budget reports applied enforcement

**Before:** `sparkwing queue list -o json` carried `budget.enforce: true` whenever
`admission.budget` included `enforce`, and the plain `budget` row printed `true` or
`false` in its sixth column. Neither said whether the OS applied a limit.

```json
{"budget": {"cores": 2, "enforce": true}}
```

**After:** `budget.enforcement` is present only when the budget asks for
enforcement. It reports what the kernel applies to the local runner right now:

```json
{"budget": {"cores": 2, "enforcement": {"applied": true, "cpu_cores": 2, "nice": 10}}}
{"budget": {"cores": 2, "enforcement": {"applied": false, "reason": "the local runner's cgroup has no CPU limit"}}}
```

The plain row's sixth column prints `enforced`, `not-enforced` or `-` (not
requested). Go callers of `pkg/wingwire` replace `BudgetState.Enforce` with
`BudgetState.Enforcement`, a `*BudgetEnforcement`.
The daemon's `QueueState.budget.enforce` and the OpenAPI
`components.schemas.pkg.wingwire.BudgetState.properties.enforce` change the same way.

- Treat `budget.enforcement.applied` as the answer to "is Sparkwing capped by the
  OS?" A missing object means enforcement was not requested.
- To ask whether enforcement was requested, read `budget.raw` for the `enforce`
  token.

## The TypeScript scaffold writes its own lockfile

**Before:** `sparkwing pipeline new --template typescript` (and
`merge-queue-typescript`) printed an `npm --prefix .sparkwing install
--package-lock-only ...` command, also reported as `setup_command` in JSON and as
a second line in plain output, which you ran before the first `sparkwing run`.

**After:** the scaffold runs that npm command itself and writes
`.sparkwing/package-lock.json`. JSON output has only `pipeline` and `path`, and
plain output prints only the pipeline name. Scripts that ran `setup_command`
can drop that step. When npm is missing or fails, the command exits non-zero
after writing the pipeline files, and its error names the npm command to run.
