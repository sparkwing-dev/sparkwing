# Migrating to v0.73.0

## Run argument values are sealed in stored runs

**Before:** `runs.request_json`, `runs.spec_json` and
`nodes.expansion_registration` held argument values, pipeline-level declared
defaults and masking registration values in plaintext.

**After:** those values live in a `sealed_arguments` envelope opened with the
secrets key. Job-level `WithArgs` defaults in `runs.plan_json`,
`nodes.spec_json` and `nodes.expansion_body` are not sealed yet. No schema change is involved. Upgrade every controller replica
before it serves new runs: a binary without argument sealing reads a sealed run
with empty argument values and refuses to resume or retry it because its seal
no longer matches. Do not downgrade a store after it has admitted runs with
arguments.

A PostgreSQL controller without a `secrets-key` credential keeps storing run
argument values, including secret defaults, unencrypted, and now warns at
startup. Add the credential to encrypt them; argument documents written while
it was keyless stay plaintext until a rotation seals them.

`sparkwing-controller restore prepare` now reads the serving controller's
`secrets-key` from `--credentials-dir`, or the generated `secrets.key` beside a
SQLite store, so it can cancel scheduled runs whose arguments are sealed. Pass
the same credentials directory the controller uses.

Runs admitted before the upgrade keep their plaintext values. On Cloud and
self-hosted controllers, run `sparkwing operator secrets rotate` to seal them,
then `sparkwing operator secrets rotate --verify` until it reports
`plaintext_run_arguments: 0`. Local stores keep those rows as written. Earlier
copies of the plaintext remain in database free space until vacuum and in
backups taken before the rotation.

## Upgrade the store in place to schema baseline 39

Store schema 39 adds the `run_event_subscriptions` and `run_event_deliveries`
tables. The controller upgrades a schema 38 store automatically; SQLite creates
its usual backup first. Existing data is unchanged and no team has a
subscription until an administrator creates one. Binaries without schema 39
support refuse the upgraded store; use a matching binary or restore its
pre-upgrade backup into a separate store.

Rotating the operator secrets key re-seals subscription signing secrets along
with team secrets and git credentials. No pipeline configuration change is
required.

## Local secrets keys follow the state home

**Before:** a redirected `SPARKWING_HOME` without an explicit key selector
could read the shared config-directory key. Its first seal failed when the
config-write guard refused to create that key outside the redirected home.

**After:** a new home creates its own `secrets.key` with mode `0600` on first
need, including controller startup. Generated and refreshed systemd and launchd
units pin their selected key file. Explicit `SPARKWING_SECRETS_KEY_FILE`
selections stay in use. The default `~/.sparkwing` home retains an existing
config-directory key even when a home-local key also exists. It never creates
another key while that config key exists.

An older redirected home that used the shared config key now refuses to open
its sealed data until that file is selected explicitly. The refusal names both
the home-local file it tried and the shared config key it skipped. It prints
the exact `SPARKWING_SECRETS_KEY_FILE=<path>` assignment that restores access.
For the usual Linux config path:

```sh
export SPARKWING_SECRETS_KEY_FILE="$HOME/.config/sparkwing/secrets.key"
sparkwing secrets list
```

Use the path in the refusal when `XDG_CONFIG_HOME` or the platform config path
differs. Keep that selector in the environment used to start this home's
controller. Reinstall an installed controller or schedule service after changing
its selectors. Stop an on-demand controller before starting it with a changed
selector. A missing or wrong key is never replaced over sealed data. Keep each
home's key with its backups.

A wrong `SPARKWING_SECRETS_KEY` value overrides every file selector. Replace
that value with the original key, or unset it before using a file. Its refusal
names the inline source and explains that precedence. The local daemon's
secret-list API returns these repairs. Standalone controller key failures keep
their credential-file repair in the controller's log, and its API returns a
generic internal error, because team members who can list secrets should not
see the server's key path.
