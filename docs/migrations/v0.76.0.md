# Migrating to v0.76.0

## Upgrade the store in place to schema baseline 40

Schema 40 installs OIDC audit privacy reconciliation. Supported stores at schema
30 through 39 upgrade in place through the existing digest-checked migration
chain. Stop older controllers, back up the database and external secrets keys,
and start the new controller with its normal secrets keyring. After schema setup,
policy configuration scrubs historical OIDC audit rows before HTTP serving.
A keyless diagnostic store open can upgrade the schema but leaves reconciliation
pending. Use configured controller startup to finish it.

If historical raw `oidc.minted` rows need scrubbing, startup requires the
external secrets keyring. A PostgreSQL controller without a `secrets-key` credential cannot
start with that history until the key is configured. With no OIDC history,
startup completes the migration without a key and writes a zero-row receipt
that omits `digest_key_id`. Keyless PostgreSQL startup remains supported in that
case. OIDC token issuance itself requires a secrets key, even when history is
empty, because every new mint must have keyed audit digests.

Before, `oidc.minted` attributes stored raw `audience` and `subject`. After, they
store `audience_digest`, `subject_digest` and `digest_key_id`. Update audit
consumers to compare both the key ID and the field's HMAC-SHA-256 digest.
Issued JWT claims, token ID, run ID, node digest and expiry keep their meanings.
See the OIDC guide's Audit investigation section for the offline recipe.

Reconciliation admits only exact precomputed changes to those historical payloads
under the binary's current schema baseline while migration version 1 is pending. Every identity, timestamp,
actor and other column stays fixed. Other updates and retention-protected deletes
remain refused. The transaction restores the unconditional update guard before
writing its `audit.oidc_scrubbed` receipt and marking completion. A failure rolls
all these changes back. Retry startup with the keyring available. A malformed
historical payload requires operator investigation before startup can finish.
Every configured startup also checks a completed migration for top-level raw
`audience` or `subject` keys. It refuses startup with a value-free error if an
older controller wrote raw rows after completion. Stop every older controller
before upgrading. This check does not re-open the append-only exception.

Rotation writes new rows with the new key ID. It never rewrites older digests.
Retain retired keys in restricted external escrow if those rows must remain
matchable after the previous key leaves the online keyring. Database-only exports
cannot test candidates, but a key holder can. Account deletion preserves these
pseudonymous digests and tracing IDs through the configured audit horizon.

SQLite's automatic pre-upgrade `.bak` file contains the old raw data. Historical
backups, SQLite free pages, WAL, PostgreSQL dead tuples, snapshots and replicas need their own
retirement. Restoring an older copy brings the raw data back until the new
controller reconciles it again. Do not downgrade an upgraded database. To run an
older binary, restore its matching backup into a separate database and treat its
raw audit contents as retained personal data. The backup and restore guide describes retention duties.

## Read verbs use list, show and status

**Before:** selected records used `describe`, `info` or `get`, and the job
diagnostics command was named `debug env`. Cache state used `cache info`.

**After:** selected records use `show`, and operational state uses `status`,
with the same flags as before:

| Before | After |
|---|---|
| `sparkwing pipeline describe --pipeline NAME` | `sparkwing pipeline show --pipeline NAME` |
| `sparkwing repos info -C PATH` | `sparkwing repos show -C PATH` |
| `sparkwing cache info` | `sparkwing cache status` |
| `sparkwing cache info --docs` | `sparkwing cache status --docs` |
| `sparkwing secrets get --secret NAME` | `sparkwing secrets show --secret NAME` |
| `sparkwing debug env --run ID --job JOB` | `sparkwing debug show --run ID --job JOB` |

An old spelling is refused with usage exit 2 and a hint naming the replacement.
Nothing runs. Update scripts that call the old spellings and regenerate shell
completion, for example with `sparkwing completion --shell bash -o plain`.

Output formats, selectors and exit codes keep their meaning. `secrets show`
reads unmasked variables. Masked secrets remain readable only by a pipeline
run that declares them. Pretty and plain output keep the value's exact bytes
without adding a newline.

`runs status --run ID --follow` keeps its lifecycle and outcome behavior.
`info --for-agent` keeps the orientation entry point. Documentation still uses
`docs read`, and collection commands still use `list`. The SDK's internal
`describe` protocol and pipeline pins keep their meaning.
SDK upgrade verification discovers the selected engine's detail command, so it
can verify both older and newer engines.

## Schedule and job argument encryption

Keyed stores seal schedule arguments and job-level `WithArgs` defaults using the
run-argument keyring.

## Upgrade the store in place to schema baseline 41

The store upgrades schema 40 to 41 in the open transaction
on SQLite and PostgreSQL. This version fence protects the changed JSON format even though the
SQL table layout stays the same. Older binaries refuse the newer store rather
than misreading encrypted arguments. SQLite takes the normal pre-upgrade backup.
A failed deployment after this schema increase requires database recovery rather
than automatic rollback to the older binary. Runner transport and plaintext hash
binding stay unchanged.
The schema-40 OIDC audit privacy migration also completes at startup on schema
41 when its pending marker remains.

Before upgrading, back up the database and its secrets keys. Stop writes and
schedule ticks while replacing every controller reader and writer with the new
version. Resume them together. Keep the current and previous keys mounted while
rotation runs.

The schema upgrade leaves existing plaintext argument rows readable until
resealed. Node specs encrypt only argument default values so SQL predicates and
metadata readers continue to work for live runs. Schedule envelope versions are
numeric, so string argument names such as `sealed_arguments` remain valid. Run
`sparkwing operator secrets rotate` after upgrading all replicas. It seals the
existing schedule declarations, overrides, override baselines, consent requests,
fire history, plans, node specs and expansion bodies in transactions. An
interrupted rotation can be repeated. The existing `plaintext_run_arguments`
count includes these documents. Run `sparkwing operator secrets rotate --verify`
until it reports `plaintext_run_arguments: 0`, `previous_key_only: 0` and no
unreadable rows, then retire the previous key. Verification writes nothing.

A keyless controller still stores argument values unencrypted. Configure its
secrets key before rotation. Retained backups and database free pages, WAL and
dead tuples can retain old plaintext after rows are sealed. Protect those copies
through their retention period. Downgrade by restoring a matching pre-upgrade
backup and its keys with writes stopped, rather than opening encrypted rows with
an older controller.
