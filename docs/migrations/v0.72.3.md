# Migrating to v0.72.3

## Random bootstrap administrator seeds

**Before:** a constant-byte `bootstrap-admin-token` could initialize a store.
**After:** that file stops controller startup, including after its bootstrap
credential was consumed or revoked. This check does not revoke credentials
already in the store. Replacing the file with a random seed cannot repair an
initialized store: its bootstrap gate remains consumed. Keep the existing store.

For a fresh store, use the generator in [authentication](../auth.md#deployment-bootstrap).
For an existing store, follow [weak bootstrap credential recovery](../auth.md#weak-bootstrap-credential-recovery).
It covers zero-grace rotation before upgrade, private recovery after a refused
restart with separate proxy/metrics listeners disabled, temporary loopback CLI
profile selection and restoration, and removal of the mounted file. The replacement credential must not
be mounted as a new bootstrap seed.

## Secure dashboard cookies

**Before:** `sparkwing-controller --insecure-cookies` dropped Secure and the
`__Host-` prefix. Helm `ingress.allowInsecure=true` permitted an ingress without
TLS. The web client could read `sw_csrf`.

**After:** Remove `--insecure-cookies` from controller invocations and delete
`ingress.allowInsecure` from Helm values. The removed flag fails as unknown.
The chart rejects the removed value, including `false`. All controllers set Secure `__Host-sw_session` and `__Host-sw_csrf` cookies, and
the web client reads only `__Host-sw_csrf`. Sign in again after changing the
browser origin. Custom browser clients must use the prefixed names.

**Why:** Secure prevents a session cookie crossing a remote HTTP connection in
clear text. Session CLI enrollment already sends the prefixed CSRF cookie and
failed against the removed mode.

Cookies have no port scope, including Secure `__Host-` cookies. Another service
on a loopback port can still receive `__Host-sw_session` and read or plant
`__Host-sw_csrf`. The Origin check and the CSRF token tied to the session protect
writes there. Do not run untrusted services on loopback alongside the dashboard.

Choose a supported browser route:

- Localhost or `127.0.0.1` needs no certificate setup in browsers that accept
  Secure cookies on loopback. Secure does not add port isolation, so keep local
  services trusted.
- Disable ingress and use `kubectl port-forward`, or use `ssh -L`, then open the
  loopback URL.
- Set chart `ingress.tls`, for example with cert-manager and Let's Encrypt.
  An enabled ingress with an empty TLS list fails rendering.
- Put Caddy in front of the native controller's `--trusted-proxy-addr` listener.
  Restrict that listener to a proxy that overwrites `X-Real-IP` and forwards
  `X-Forwarded-Proto: https`.

See [Serving the dashboard over HTTPS](../self-hosting.md#serving-the-dashboard-over-https)
for commands and chart values.
