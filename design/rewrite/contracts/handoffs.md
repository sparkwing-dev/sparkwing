## WS4 integration: one refill payment call

Under decision 67 a refill takes one authenticated checkout-service call,
`POST /internal/refill`, with the request fields `team`, `deployment`,
`refill_id`, `amount_cents` and `customer`. It responds with `payment_intent`,
the Stripe `status` and, when Stripe refused the charge, `failure`
(`authentication_required` or the decline code). Under decision 65 the
controller sends no card or email: the service charges the customer's default
payment method, or its newest card when it has no default, and answers 409
when the customer has no card. Both repositories test their real code against a
byte-for-byte copy of `testdata/checkout_contract.json`, which covers every
checkout-service route, the payment bounds, the Stripe metadata keys and which
refusals are final.

- The controller checks eligibility and opens the refill in one transaction:
  refills on, no failed refill blocking them, no hold, balance below the
  threshold and every limit respected. No transaction stays open across the
  provider call.
- The service creates the PaymentIntent with `confirm=true` and
  `off_session=true`, with the refill id as the idempotency key and as the
  `refill_id` metadata. The service charges whatever it is asked, so every
  controller pass rechecks eligibility, setting the open refill's own
  reservation aside, immediately before repeating its same request. A crash or
  lost answer never charges twice. A refill no longer eligible is withdrawn
  without another call, and a payment an earlier call made still credits it.
- The signed payment webhook finds the refill by the `refill_id` in its
  metadata and settles it exactly like Add funds; a refill funds at most one
  payment. A 409 closes the refill as `no_card`; a `failure` closes it with that
  code. Both block refills like a declined payment and notify the owners, and
  only a successful Add funds or a new card setup clears the block.
- `POST /internal/portal` takes `team`, `deployment` and `customer` and returns the
  `url` of a Stripe customer portal session, where owners view, replace or remove
  the card. `POST /internal/card-setup` also receives the team owner's `email`,
  which only Stripe keeps, for receipts. `POST /internal/refund` takes
  `deployment`, `payment_intent`, `key` and `reason`.
- The service answers 403 to portal, refill, card setup with an existing
  customer and refund when the Stripe customer or payment intent is stamped
  for another deployment. The controller follows payment and setup pages only
  on `checkout.stripe.com` and the portal only on `billing.stripe.com`.

## 2026-10-20 Korey decision 36: member tokens are decoupled from session timeout

- A member token minted from a session keeps its own expiry (default and ceiling 90 days) and reports that date. The minting session remains its parent only for explicit revocation: logout, membership removal or demotion (epoch fencing), and admin revocation kill it immediately. A session merely timing out (idle or absolute) does not expire its tokens. Matches GitHub personal access tokens.

## 2026-10-20 Korey decision 37: concurrency groups split by level; no run-level box scope

- Run-level (plan) groups and job-level groups live in separate namespaces. The same key declared at both levels names two different groups, so a run holding plan group X can never block on another run's job group X. This removes the plan/job wait cycle that one shared namespace allowed.
- Run-level groups cannot be box-scoped. A run has no single execution host, so a machine scope at run level has no meaning; declaring one is refused when the pipeline is accepted, with an error that names the group and points at job-level box scope. Box scope stays available for job-level groups.
- The raw API for acquiring a group directly (`/api/v1/queue/groups/{group}` acquire, heartbeat, release, cancel and resolve) is deleted pre-launch. Every acquisition goes through the single admission owner.

## 2026-10-20 Korey decision 38: a run that loses its run-level group waits to reacquire it

- When a run's hold on a run-level group lapses (controller or host lost contact past the lease) and another run takes the group, the first run is not cancelled. Jobs already released keep running to completion; no further job is released until the run reacquires the group, and it queues for it like any other waiter. The run shows that it is waiting to reacquire the named group.
- Rationale: once the lease has lapsed the overlap has already happened, so cancelling cannot undo it, and killing a half-finished deploy is usually worse than finishing it. Waiting also keeps the run's remaining work instead of forcing a rerun.

## 2026-10-21 Korey decision 39: audit rows carry no personal data; retention by age

- Audit rows are append-only and name people only by account id and invitations only by invitation id, never by email or other personal data. Personal data lives on the account record; deleting the account leaves its audit entries naming a deleted account with no route back to the person. This replaces the old business_events scrub on account deletion. Matches GitHub's audit log, which keeps entries for deleted users under a placeholder.
- The append-only guard itself permits deleting rows older than the retention horizon (decision 15: 400 days, operator-set); a retention job prunes them. Rows inside the horizon cannot be updated or deleted by any code path.

## 2026-10-21 Korey decision 40: audit append-only is a guard against application code, not credential theft

- PostgreSQL keeps one database role that owns the tables and runs the app. The append-only trigger stops application code from changing audit history; it does not stop a holder of the app's database credentials, who could disable it (and could already read every secret). Docs say "append-only against application code", not "tamper-proof". The no-op REVOKE is removed rather than kept as an implied control.
- Separate owner and runtime roles (migrations as owner, controller as a restricted role) are post-launch hardening.

## 2026-10-21 Korey decision 41: webhook deliveries are never retried automatically

- A push that arrives while the team is out of credits does not queue. It is recorded as a run that did not start because credits were exhausted, visible in the run list, with a "run now" action once the team has funds. Matches GitHub Actions, where a workflow over a spending limit fails to start rather than waiting.
- A stored delivery whose processing fails (temporary or permanent) is not retried automatically. It is marked failed with its reason and listed for team admins on the team settings page ("pushes we couldn't process") with a manual "process again" action, like GitHub's Recent deliveries -> Redeliver. Retention purges failed rows on the same schedule as completed ones.

## 2026-10-21 Korey decision 42: a job's predicate runs inside its concurrency slot on the executing host

- SkipIf and memo checks run as the first step of the job, on the host that executes it, under the job's actual award, after the job's concurrency groups are acquired there. A skip releases the groups and ends the job. The coordinator never acquires job groups for evaluation. This keeps the guarantee that a predicate sees the state its group protects (e.g. "skip if already deployed" under a deploy group) and removes the cross-host wait cycle. Cost: a job that will skip still queues behind its group and briefly holds a machine.

## 2026-10-21 Korey decision 43: one host-side masker; short secrets refused

- Masking is owned by the Go host alone (design: simplicity/HOST-EGRESS-MASKING.md). Output is masked as a byte stream at host egress before it is split into lines, persisted, sent or displayed; protocol payloads are sanitized before the host builds trusted envelopes. The host registers every secret from the sealed accepted run (one normalized registration projection, list items included) before author code runs, and registers lazily issued values (stored secrets, OIDC tokens) before releasing them. SDKs contain no masker and send no automatic registrations; explicit Mask for author-generated credentials remains. Pipeline code run without a Sparkwing host gets no masking.
- A secret value shorter than 4 characters, or containing `***`, is refused when stored or declared, with an error saying to use a plain config variable instead. This applies to each item of a list secret. Matches CircleCI, which does not mask values under 4 characters.

## 2026-10-21 Korey decision 44: runner sizes are labels; one claim query; receipts for every delivery effect

Runner size is a label: Cloud runners carry a fixed set of size labels (e.g. `sparkwing-4cpu`), self-hosted runners advertise any labels, and a job runs only where a runner has every label it requests (GitHub larger-runner model). Billing prices by the size label's class.

## 2026-10-21 Korey decision 45: one admission owner in the store

## 2026-10-21 Korey decision 47: restore payment recovery is a manual runbook

## 2026-10-26 Korey decision 70: OIDC claims for host kind, fetched repositories and Actions

- OIDC tokens carry a runner environment claim saying whether the job ran on a fresh host (launcher pod, Cloud pod, GitHub Actions job) or a persistent one (plain machine, persistent runner, personal machine, here), like GitHub's runner_environment, so deploy roles can require fresh hosts.
- Runs whose repository is proven because Sparkwing fetched the code from it (decision 68 run-now refinement) carry the repository claim; ref and sha claims stay off for them because their trust class is manual.
- Runs from GitHub Actions bindings say trigger:actions in their subject, not trigger:manual.
- Decision 68's secrets rule reads: pipeline secrets go to runs whose repository is proven, either verified (App delivery, Actions, admin-armed schedule) or fetched by Sparkwing from the repository at a branch or tag head (run-now, console runs, unlocked schedules); uploads, local, here, raw commits and pull request refs get shared secrets only.

## 2026-10-27 Korey decision 71: no runtime network probes; network policy is the operator's job

- Sparkwing does not probe network enforcement at job launch or at launcher start. The launcher keeps applying the Cloud job network rule (block cloud instance metadata and private/cluster-internal ranges; outbound internet open on any port, like other CI providers), and the docs state that the cluster must enforce NetworkPolicy. Verifying enforcement is an operator check run periodically (for Sparkwing Cloud, Korey's own checks, e.g. with stormwing), not a guarantee the product makes to self-hosters.
- The per-job boundary probe machinery and decision 69's kubelet exception are deleted.

## 2026-10-27 Korey decision 72: fetched runs carry their branch in OIDC

- Amends decision 70. A run whose code Sparkwing fetched from the repository through the App at a branch or tag head (run-now, console runs, unlocked schedule overrides) carries the ref and sha it ran in its OIDC token, alongside the repository claims, with trigger manual. The branch head was resolved and verified by Sparkwing, so it is the source of truth, matching GitHub's workflow_dispatch tokens. Deploy policies that pin ref:refs/heads/main accept a run-now on main and refuse one on another branch; policies that care how a run started can require trigger:push. Uploads, local and here runs still carry no repository or ref claims.
